Objet et portée

Ce dossier fournit à l’équipe IT les informations nécessaires pour héberger Mining 360 sur BODEFM et intégrer l’authentification des utilisateurs avec leur compte Windows d’entreprise via Microsoft Entra ID.

Décision d’architecture
L’authentification web recommandée est Microsoft Entra ID avec OpenID Connect / OAuth 2.0 Authorization Code. Elle fonctionne sur Windows, macOS, iOS, Android et les navigateurs modernes. Elle ne dépend pas d’un poste Windows et ne transmet jamais le mot de passe du domaine à Django.

Destinataires

Identity & Security

Entra ID, permissions Graph, Conditional Access, secret/certificat, comptes de service.

Infrastructure

BODEFM, DNS, TLS, IIS, service applicatif, pare-feu, supervision et sauvegarde.

Database

SQL Server, base Mining360App, identité de service, chiffrement et droits minimaux.

01 · Résumé exécutif

Ce que l’IT doit créer

Identité

  • Une App Registration Microsoft Entra ID mono-tenant.
  • Un Enterprise Application limité aux groupes autorisés.
  • Les permissions Graph minimales avec consentement administrateur lorsque requis.
  • Un credential applicatif protégé et rotatif.

Hébergement

  • Un DNS interne et un certificat TLS.
  • IIS + ARR/URL Rewrite, ou reverse proxy équivalent validé.
  • Un service Windows pour le runtime Django.
  • Un répertoire applicatif et des ACL dédiées.

Données

  • Base Mining360App sur SQL Server.
  • Login Windows de l’identité de service.
  • Droits DDL temporaires pour les migrations et droits DML à l’exécution.
  • Backups, supervision et rétention.

Réseau

  • HTTPS utilisateurs vers BODEFM.
  • BODEFM vers Entra, Graph et fournisseurs autorisés.
  • BODEFM vers SQL Server et Power BI.
  • SSH 22 limité aux contrôleurs de déploiement approuvés.

Séparation des bases
Mining360App est la base applicative Django. MiningProd reste une source opérationnelle externe et ne doit pas devenir la base interne de Django. SQLite est limité au développement/migration et n’est pas un mécanisme de production ni de rollback.

Prérequis runtime

Django ne fournit pas de serveur de production. L’IT doit valider et exploiter un serveur WSGI Windows, par exemple Waitress, lancé comme service Windows sous l’identité de service. IIS termine TLS et transmet uniquement vers l’écoute locale du WSGI.

04 · Authentification

Authentification Windows web

Dans ce dossier, “authentification Windows” signifie que l’utilisateur se connecte avec son identité Microsoft d’entreprise. Mining 360 ne reçoit et ne stocke jamais son mot de passe Active Directory.

1. Utilisateur
compte entreprise
›
2. Microsoft Entra ID
authentification + MFA
›
3. Callback Mining 360
code d’autorisation
›
4. Graph /me
profil vérifié
Demande de connexion. Mining 360 génère un état aléatoire et redirige le navigateur vers l’endpoint du tenant Entra.
Authentification Microsoft. Entra applique mot de passe, MFA, appareil conforme et Conditional Access selon les politiques IT.
Retour contrôlé. Entra redirige vers /auth/callback/. L’URI doit correspondre exactement à celle enregistrée.
Échange serveur à serveur. Django échange le code avec le client ID et le credential applicatif.
Profil. L’application appelle Graph /me et récupère id, displayName, UPN, mail et jobTitle.
Autorisation Mining 360. Le profil doit exister et être actif dans PlatformUser; ses modules et rôles déterminent ce qu’il peut utiliser.

Ce mécanisme n’est pas

  • une transmission du mot de passe Windows à Mining 360;
  • une authentification LDAP directe;
  • une délégation Kerberos IIS vers Django;
  • une autorisation automatique basée uniquement sur l’appartenance au domaine.
Expérience SSO actuelle
Le code ajoute actuellement prompt=select_account. L’utilisateur bénéficie de sa session Microsoft, mais voit le sélecteur de compte. Une connexion réellement silencieuse nécessite une évolution applicative contrôlée (suppression de ce paramètre ou utilisation d’une bibliothèque Microsoft supportée), puis des tests Conditional Access.

Credential applicatif

Recette immédiate

Créer un client secret de courte durée selon la politique IT. Transmettre la valeur une seule fois via le coffre-fort approuvé. Configurer une alerte d’expiration et une rotation avec chevauchement.

Production cible

Microsoft recommande un certificat plutôt qu’un secret. L’implémentation actuelle attend un client secret; le support certificat nécessite une évolution du service d’authentification avant activation.

Valeurs à remettre à l’équipe Mining 360

  • Tenant ID de l’annuaire.
  • Application (client) ID de Test et de Production.
  • Object ID de l’Enterprise Application.
  • URI de redirection validées.
  • Référence sécurisée du credential, sans l’inscrire dans un ticket en clair.
  • Groupes assignés et propriétaires de l’application.
  • Date d’expiration et processus de rotation.
Ne pas réutiliser l’App Registration Power BI en production
Le code tolère actuellement un fallback vers POWERBI_TENANT_ID, POWERBI_CLIENT_ID et POWERBI_CLIENT_SECRET. Pour la séparation des responsabilités et des permissions, créer des identifiants Entra propres à l’authentification Mining 360.

Principe du moindre privilège
Ne pas accorder Directory.Read.All si User.Read.All suffit. L’application ne modifie aucun utilisateur Entra et n’a pas besoin de permission Graph en écriture.

Gouvernance recommandée

  • Consentement administrateur documenté pour les permissions Application.
  • Au moins deux propriétaires nommés sur l’App Registration.
  • Enterprise Application avec “Assignment required = Yes”.
  • Groupe Test séparé du groupe Production.
  • Conditional Access conforme aux règles de l’entreprise : MFA, risque, localisation et appareil.
  • Revue périodique des utilisateurs assignés et des administrateurs Mining 360.
  • Surveillance des journaux Entra Sign-in et Service Principal Sign-in.

DNS et certificat

  • Créer un enregistrement DNS interne stable vers BODEFM ou vers le load balancer.
  • Émettre un certificat TLS dont le SAN contient exactement le FQDN.
  • Installer la chaîne complète dans le magasin de certificats Local Computer.
  • Configurer le binding IIS 443 et interdire HTTP ou rediriger proprement vers HTTPS.
  • Enregistrer ce même FQDN dans MINING360_ALLOWED_HOSTS, CSRF_TRUSTED_ORIGINS et dans l’URI Entra.

Reverse proxy IIS

IIS termine TLS. ARR + URL Rewrite transmettent les requêtes à http://127.0.0.1:8000. Le port applicatif ne doit pas être exposé sur le réseau. Conserver les headers Host et X-Forwarded-Proto=https, définir des timeouts compatibles avec Power BI et limiter les uploads.

Configuration Django derrière proxy
Avant production, activer dans les settings le traitement sécurisé du proxy : SECURE_PROXY_SSL_HEADER, cookies Secure/HttpOnly/SameSite, HSTS après validation, redirection HTTPS et origines CSRF explicites. Ces paramètres ne sont pas encore complètement configurés dans le fichier actuel.

  • Les secrets ne sont visibles ni dans l’interface ni dans les journaux.

10 · Déploiement

Installation BODEFM

Préparer l’OS. Patches, antivirus, NTP, DNS, certificat, IIS, ARR/URL Rewrite, ODBC Driver 18 et Git ou package offline.
Créer l’identité. gMSA/service account, droits service, SQL et ACL minimaux.
Créer les répertoires. C:\Mining360\app, venv, logs, shared\static, backups et secrets.
Installer la release. Checkout d’un tag/commit approuvé ou extraction d’un package contrôlé par checksum.
Créer l’environnement Python. Installer les dépendances verrouillées dans le virtualenv.
Configurer. Variables au niveau service, secrets par référence, SQL et Entra séparés.
Valider avant changement. Connexion SQL, manage.py check --deploy, migrations en attente et backup.
Appliquer. migrate --noinput, collectstatic --noinput, puis démarrer/recycler le service WSGI.
Publier. Configurer IIS, tester la règle de proxy, le certificat et le hostname.
Accepter. Health checks, connexion Entra, rôles, SQL, Power BI et journalisation.

Commandes applicatives contrôlées

cd C:\Mining360\app
C:\Mining360\venv\Scripts\python.exe -m pip install -r requirements.txt
C:\Mining360\venv\Scripts\python.exe manage.py check --deploy
C:\Mining360\venv\Scripts\python.exe manage.py migrate --noinput
C:\Mining360\venv\Scripts\python.exe manage.py collectstatic --noinput
Aucun lancement production avec runserver
python manage.py runserver n’est pas conçu pour la production. Le service Windows doit exécuter un serveur WSGI adapté et être supervisé avec redémarrage, compte dédié et rotation des logs.

Rollback minimum

  1. Arrêter le service applicatif.
  2. Conserver les logs et la base défaillante pour diagnostic.
  3. Restaurer le backup SQL validé si la migration l’exige.
  4. Remettre la release précédente.
  5. Réappliquer les migrations compatibles, redémarrer et exécuter les tests de santé.

Rétention et sauvegarde

La politique IT doit définir la fréquence de sauvegarde de Mining360App, la rétention des fichiers Resources, la restauration testée, les logs de sécurité et la protection des clés de chiffrement. Une sauvegarde sans les clés stables de chiffrement et MINING360_SECRET_KEY peut rendre des données applicatives inutilisables.
